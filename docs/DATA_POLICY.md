# Data policy

Sounding uses **synthetic stimuli and public sources only**.

## Never in this repository

- Real customer messages, transcripts, complaints or case notes, in any form,
  including paraphrased, anonymised or "inspired by" versions.
- Anything from an employer: data, documents, internal guidance, system
  prompts, product names, or metrics.
- Details of any real, identifiable person.
- API keys or other secrets. Keys go in a local `.env`, which is git-ignored.

## Allowed

| Provenance kind | Meaning |
| --- | --- |
| `synthetic-handwritten` | Written by a project author for this project, describing nobody. |
| `synthetic-template` | Assembled by this package from handwritten parts. |
| `synthetic-llm` | Generated by a model, then reviewed by a human before use. |

Public documents may be cited and used for categories and definitions. Each one
must be registered in `PUBLIC_SOURCES` in `src/sounding/provenance.py`. The
current registry holds FCA guidance FG21/1 (the four drivers of vulnerability)
and the Consumer Duty.

## How it is enforced

- Every stimulus record carries a `provenance` block. `validate_record` rejects
  any record whose kind is not on the list above or whose sources are not
  registered.
- `validate_record` also rejects text matching personal-data patterns: email
  addresses, UK phone numbers, National Insurance numbers, postcodes, sort
  codes and long digit runs.
- The test suite scans every data file in the repo for those patterns, and CI
  runs it on every push.
- Generated stimuli and eval logs are git-ignored; only the seed bank is
  committed.

Pattern checks cannot prove a sentence is synthetic. The rule that matters is
the first one: write stimuli from imagination and public guidance, never from
memory of real cases.

## Human raters

Raters for intensity scaling and judge validation see only synthetic stimuli.
Store their judgements under a rater code, never a name.
